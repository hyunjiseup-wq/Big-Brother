# 재검사 인계·장애 검증·오래된 큐 정리

## 검수 기록 인계의 보장 범위

재검사 큐의 자동 증가 ID를 `violation_log.retry_queue_id`에 연결한다. 같은 ID의 검수는
유니크 인덱스로 한 건만 허용한다. `BEGIN IMMEDIATE` 트랜잭션에서 큐의 서버·채널·메시지
일치를 확인한 뒤 검수 기록, KPI outbox, 큐 삭제를 함께 커밋한다. 오류나 취소로 롤백하면
큐가 남는다. 이미 큐가 완료된 동일 ID 요청은 기록 생성과 카드 전송을 하지 않는다.
같은 메시지가 이후 다시 보류되면 새로운 큐 ID이며, 예전 실행이 새 큐를 삭제할 수 없다.

위반 후보는 수동 검수로만 인계한다. 실제 제재를 이 재검사 루프에서 자동 재실행하지 않는다.
정상·삭제된 메시지는 검수 생성 없이 큐를 완료한다. 제재 전 원문 재조회가 일시 실패하거나
내용이 바뀌면 완료하지 않고 최신 내용으로 재검사한다. 실시간 AI 워커와 보류 큐가 겹쳐도
같은 인계 경로를 사용한다.

카드는 검수 커밋 후 전송한다. 처음에는 `card_delivered=0`, 전송 성공 확인 후에만 1로 바꾼다.
전송 전 종료나 전송 실패여도 검수 자료는 남고 `!BB 검토대기`에서 카드 없는 기록으로 보인다.
조회 기본 기간 밖의 오래된 미전송 기록은 DB에서 보존되지만 별도 운영 조회가 필요하다.
Discord 전송 성공 직후 DB 갱신 전 종료 시 실제 카드가 있어도 미전송 표시가 남을 수 있다.
분산 시스템의 전송까지 정확히 한 번이라고 보장하지 않는다. 자동 재전송하지 않고 운영자가
서버 카드와 검수 번호를 먼저 대조한다. 검수 기록 중복과 자동 제재 재실행은 방지한다.

## 실제 연결 장애·복구 검증 방법

`python -B discord_reconnect_check.py`

- `bot.py`를 시작하지 않는 별도 `discord.Client` 진단이다. 메시지 수신 의도도 요청하지 않는다.
- 운영 봇과 같은 단일 실행 잠금을 점유한다. 운영 봇 실행 중이면 거부한다.
- 현재 토큰은 Discord 공식 API와 Gateway 연결에만 사용한다. 토큰·세션 ID·사용자 ID를 출력하지 않는다.
- READY → REST 조회 → 진단 WebSocket 닫기 → disconnect → RESUMED/READY →
  새 WebSocket 확인 → REST 동일 계정 조회 → 진단 종료 순서로 검사한다.
- PC 네트워크 설정·방화벽은 건드리지 않으며, 실제 메시지·제재·운영 DB 쓰기도 없다.
- 검증은 이 PC/토큰/설치된 discord.py의 실제 Gateway 단절 복구다. 통신사 장애나 장시간
  Discord 전면 장애, 운영 봇의 모든 백그라운드 기능을 재현한 검증으로 확대 해석하지 않는다.

## 탈퇴 서버의 오래된 큐 정리 기준

자동 삭제는 사용하지 않는다. `python -B retry_queue_report.py`는 SQLite `mode=ro`로 읽고
조사 후보 수만 보여준다. 존재하지 않는 DB도 새로 만들지 않는다.

조사 후보 조건(모두 충족):

1. 큐 생성 후 30일 이상 경과.
2. 총 재시도 횟수 3회 이상. 이는 서버 조회 실패가 연속 3번이라는 뜻이 아니다.
3. 마지막 실패 사유가 정확히 `discord_guild_unavailable`.

이 조건은 삭제 승인이 아니다. 실제 삭제를 검토하려면 다음 증거를 추가로 확보한다.

1. 정상 인증된 동일 봇 계정의 공식 `GET /users/@me/guilds` 전체 페이지 조회에서 대상 서버가
   없음을 확인한다. 페이지 일부만 읽은 경우 증거로 인정하지 않는다.
2. 첫 조회로부터 최소 24시간 뒤 정상 연결에서 다시 전체 목록 부재를 확인한다.
   조회 실패·레이트 리밋·403/404·로컬 캐시 누락은 부재 증거로 대신하지 않는다.
3. 관리자에게 실제 탈퇴/추방 및 재초대 계획 없음을 확인받고 해당 서버·큐 ID 단위 승인을 남긴다.
4. 삭제 직전에도 서버 재가입 여부를 다시 확인한다. 재가입·불확실성 발견 시 중단한다.
5. 최신 SQLite 온라인 백업 및 무결성 검사를 마친 뒤 정확한 큐 ID·서버 ID·메시지 ID·갱신 시각을
   대조한다. 승인 후 내용이 바뀐 행은 제외한다. 큐 외의 검수·제재·학습 기록은 삭제하지 않는다.
6. 삭제는 별도 명시적 운영 작업으로 진행한다. 승인자, 확인 시각, 대상 ID, 사유, 처리 건수,
   복구할 백업 위치를 비공개 운영 로그에 남긴다. 광범위한 서버별 일괄 삭제는 금지한다.

이 문서와 집계 도구는 실제 삭제 명령을 제공하거나 수행하지 않는다. 재가입 계획이 있거나
증거가 부족하면 보존한다. 오래됐다는 이유로 미처리 메시지를 정상 판정으로 바꾸지 않는다.

  README 검사 2건도 별도 통과했다. 운영 DB 스키마 변경은 실행하지 않았으며,
  다음 정상 봇 시작의 기존 `init_db()` 경로에서 새 컬럼·인덱스가 적용된다.

## 추가 감사 — 프로세스 강제 종료 경계

별도 자식 Python 프로세스에서 실제 `create_review_record()`를 실행하고,
SQLite 커밋 직전과 직후에 `os._exit()`로 프로세스를 즉시 종료하는 테스트를 추가했다.
운영 DB가 아닌 임시 WAL DB를 사용하며, Python의 finally/연결 닫기 없이 종료한다.

- 커밋 직전 종료: 큐 1건, 검수 0건, KPI outbox 0건. 다시 처리하면 검수 1건으로 정상 인계.
- 커밋 직후 종료: 큐 0건, 검수 1건, KPI outbox 1건. 동일 번호 재호출은 무동작이며
  미전송 검수 1건을 조회할 수 있다.
- 두 경우 모두 종료 후 DB 무결성 검사 통과. 이는 프로세스 중단 검증이지 디스크 고장이나
  PC 전원 차단까지 재현한 검증은 아니다.
- 동일 날짜 실연결 재확인: `RESUMED`, 새 WebSocket, 복구 후 REST 조회 성공, 0.877초.
- 운영 DB 재조회: 대기 1건, 가장 오래된 기록 약 35일, 조사 후보 0건. 변경·삭제 없음.
- 최종 전체 회귀 테스트 297건 통과(51.563초), 실패·건너뛰기 0건.
